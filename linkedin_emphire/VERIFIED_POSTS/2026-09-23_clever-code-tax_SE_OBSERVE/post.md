Funny enough — the worst code I ever wrote was the code I was proud of.

I don't mean the bugs. I mean the clever parts.

I spent a whole weekend once building a beautiful abstraction. Generic, reusable, five layers deep, named something that made me feel smart. Teammates looked at it and said "wow, that's clean."

Three months later nobody could extend it. Including me.

The new hire spent a week trying to understand the one function that did nine things. The senior dev on the team looked at it for twenty seconds and said "why didn't you just write three boring functions?"

He was right.

Here's the thing nobody tells you when you're learning: clever code is a tax. You pay for it once when you write it (feels amazing), then everybody who touches it pays for it forever.

Boring code — the obvious thing, the thing a junior could read at 9 AM Monday and understand — that's the actual superpower.

→ Long variable names beat short clever ones
→ Three obvious functions beat one clever one
→ Duplication that's easy to delete beats an abstraction built for a future that never comes
→ Comments explaining *why* beat code that's trying to be self-documenting
→ The code you delete is just as important as the code you ship

People talk about senior engineers like they write more complex code. The best ones I've worked with write the simplest code that solves the problem.

One rule I ship by now: if I'm proud of how clever a piece of code is, I probably need to rewrite it.

The code that survives isn't the smartest. It's the code the next person can read without hating you.
